Guias e processos

Como abrir uma discussão de suporte

Tema: Canal de suporte

No repositório de suporte, clique em New Discussion, escolha a frente (Design System, ContentOps, Acessibilidade etc.) e clique em Get Started. Dê um título claro, descreva a dúvida com o máximo de detalhes e anexe prints ou o link do arquivo no Figma. Em Labels, marque a equipe responsável (Design System, ContentOps ou Acessibilidade) e a BU (B2C, B2B, E-comm e Portais, DesignOps, Pesquisa e Evolução, Design Horizontal ou Outros); pode marcar mais de uma. Ao publicar, a discussão ganha um número para acompanhamento.

Como solicitar a validação de jornada para System Ops

Tema: Validação de jornadas

  • A validação é obrigatória e acontece antes do handoff para desenvolvimento: é a etapa final do projeto. As telas devem estar na página de Handoff do arquivo.
  • Antes de enviar, é obrigatório rodar o plugin de validação de System em todas as jornadas que usam o Design System (ver o guia do plugin).
  • Passos: (1) preencha o formulário oficial de validação de jornada no repositório; (2) informe o link da página/frame a validar (preenchido na 1ª validação, atualizado a cada rodada e mantido no arquivo como histórico); (3) use o componente Notas da biblioteca Helper (Handoff & Acessibilidade) para registrar feedbacks; (4) consulte o guia "Erros comuns na validação de jornadas" antes de abrir o chamado; (5) qualquer alteração depois da aprovação exige revalidação (no mesmo ticket ou como subtarefa).
  • O time de Ops deixa notas no arquivo com os ajustes. Elas só podem ser removidas depois da aprovação. Durante a validação, o designer não deve alterar a estrutura do arquivo.
  • Status registrados no histórico do Figma: 🔵 início da validação · 🟠 validação com pendências (o designer corrige e disponibiliza de novo) · 🟢 aprovada · 🔴 reprovada.
  • ⚠️ Se os ajustes não forem feitos em 30 dias, a validação é reprovada e o ticket é fechado. Para recomeçar, é preciso abrir nova solicitação.

Ref. #38 · 10/2024

Como o time de System Ops valida uma jornada

Tema: Validação de jornadas

O time confere se a jornada está pronta para handoff, estruturada na página de Handoff do Figma, com histórico claro de validações e com uso adequado do Design System (ou da biblioteca legada). O time localiza a solicitação de validação aberta; se faltar informação essencial, pede ajuste no próprio ticket antes de começar. Usa o componente Notas (biblioteca Helper) e um checklist padrão de System Ops. A partir do início da validação, o designer não deve alterar a estrutura do arquivo: os ajustes pedidos são feitos depois. Status: 🔵 início · 🟠 aguardando correções · 🟢 aprovada · 🔴 reprovada. Ajustes não feitos em 30 dias reprovam a validação. Ao concluir, o time comenta no ticket o status da jornada.

Erros mais comuns na validação de jornadas no Figma

Tema: Validação de jornadas

(corrija antes de pedir a validação):

  1. Color styles de bibliotecas descontinuadas (ex.: a biblioteca antiga da marca, marcada como deprecated). Acontece ao copiar telas de arquivos antigos, usar componentes de fora das bibliotecas oficiais, não atualizar componentes ou colar textos sem Paste and match style. Correto: cores como variables (ícone quadrado no painel) vindas da biblioteca Skins do Design System. Se a cor continuar errada após atualizar, use Reset instance ou puxe uma nova instância da aba Assets. Exceções: gradientes (o Figma não suporta gradiente em variable, então ficam como color style) e elementos externos com cores próprias (ex.: logo de bandeira de cartão, em hexadecimal).
  2. Cor errada no fundo da tela (hexadecimal #FFFFFF direto, ou color styles antigos). Correto: variables background (fundo branco) ou backgroundAlternative (cinza claro), da biblioteca Skins. Exceção: os componentes de sucesso de fim de fluxo (Success Feedback e Success Feedback Screen) usam a cor brand de fundo.
  3. Text styles de bibliotecas descontinuadas. Correto: text styles da biblioteca Skins, atualizados. Se continuar errado, Reset instance. Ao colar textos, use Paste and match style (Cmd+Shift+V). Exceção: alguns componentes não usam text style e sim variables separadas (font size, line height, font weight); confira se a instância mantém as mesmas variables do original.
  4. Telas sem Layout guide do Design System. Aplique o Layout guide adequado à largura: até 767px → Mobile; 768–1023px → Tablet; 1024–1511px → Desktop; 1512px ou mais → Large Desktop. E ao layout: templates 8+4, 6+6, 5+4, 4+6, 3+9 ou 12 (sem template).
  5. Alterar manualmente propriedades de componentes. Ex.: para um Button Primary menor, use a propriedade booleana Small, nunca mude font size, line height ou padding na mão. Se a variação não existe como propriedade, não altere o componente. Sempre confira as propriedades disponíveis e não mexa em gap, padding, texto ou cor pelo painel.
  6. Componentes da biblioteca Extended liberados para uso têm o sufixo (ext) (ex.: Data Progress (ext), Detailed Card (ext), Input Large (ext), Toggle Icon (ext)). Não use text styles da Extended: todos já existem na biblioteca Skins.
  7. Outros erros frequentes: não nomear os frames; usar divider na última Row de uma lista; usar só Text Field num formulário que pede dados diferentes (telefone, CPF, data → use os campos específicos); usar mais de um Callout na mesma tela; usar a tela de feedback errada (ex.: Info Feedback Screen num erro de fim de fluxo, em vez de Error Feedback Screen); posicionar a Snackbar no lugar errado; usar ícone que não existe na biblioteca de ícones; usar cores incorretas em ícones; usar Nav Bar da biblioteca Extended em vez da biblioteca Modules ou da biblioteca Mobile.

Plugin de validação de System (Figma)

Tema: Ferramentas > Plugin de validação

Apoia a validação de jornadas que usam o Design System, apontando erros básicos antes da revisão. É obrigatório rodá-lo antes de pedir validação. Como usar: no Figma, Resources (Shift+I) → Plugins & Widgets, busque o plugin e clique em Run. Na interface: escolha a plataforma (Mobile ou Desktop) conforme a tela; Scan verifica frame, seleção ou página; setas navegam pelos erros e um contador mostra o total; Marcar todos / Desmarcar marcam os erros; Restaurar instâncias com erro corrige componentes (só funciona dentro de frames). No modo expandido há as abas de visão geral, Pro Mode, Marcados e Detach, filtros por tipografia e tokens de cor e marcação por categoria. Boas práticas: selecione a plataforma certa antes do scan e combine o plugin com revisão manual.

Ref. #928 · 03/2026

Playroom

Tema: Ferramentas > Playroom

Ambiente de código voltado ao design para criar mockups e protótipos com os componentes reais do Design System, testar e compartilhar. Tem trechos (snippets) prontos de quase todos os componentes e permite ver vários temas e tamanhos de tela ao mesmo tempo. <PreviewTools/> no início adiciona uma barra para trocar a marca e o modo claro/escuro (opções como flutuante e showPlatformSelector).

  • Atalhos: ⌘+S formata o código; ⌘+K abre snippets; ⌥+↑/↓ move a linha; ⇧+⌥+↑/↓ duplica a linha; ⌘+⌥+↑/↓ adiciona cursor; ⌘+D seleciona a próxima ocorrência; ⌘+Z desfaz.
  • Básico de JSX: componentes começam com maiúscula (camelCase); tudo entre a tag de abertura e a de fechamento é children; elementos sem filhos podem fechar sozinhos (<Componente/>).
  • Props: formato nome={valor}. Texto entre aspas (title="Título", sem chaves); número entre chaves (space={16}); booleano (isInverse={true}, ou só isInverse, que equivale a true). Apertar Espaço dentro da tag mostra as props disponíveis.
  • Estilos: dá para usar <style> com classes e className, ou style={{...}} com propriedades CSS em camelCase (gridTemplateColumns).
  • O guia também cobre lógica por tamanho de tela, marca e modo claro/escuro, layouts (Responsive Layout, Grid Layout, Box, Stack, Inline, Carousel), estados e listas.

Como criar layouts de acordo com o Design System

Tema: Layout e grid

  • Responsive Layout controla os breakpoint ranges e as margens laterais. São 4: Small, Medium (768–1023px), Large (1024–1511px) e Extra Large. Em Small, Medium e Large as margens são fixas e a área útil varia; em Extra Large a área útil é fixa e as margens crescem com a tela.
  • Grid Layout distribui o conteúdo em colunas; quantidade, largura das colunas e gutter mudam por breakpoint. Templates (úteis em Large e Extra Large): 6+6; 8+4; 4+6 (esquerda nas colunas 1–4, direita 6–11); 5+4 (esquerda 2–6, direita 8–11); 3+9. Os templates não são obrigatórios, mas são recomendados.
  • No Figma não existem componentes Responsive Layout nem Grid Layout: a biblioteca Desktop do Design System tem Layout guides equivalentes. Para aplicar: adicione a biblioteca Desktop → selecione o frame → no painel direito, Layout guides → Apply styles (ícone de 4 bolinhas) → escolha a opção. Shift+G mostra/esconde o guia. Mesmo sem template, aplique um Layout guide da categoria 12. Larguras: Mobile 320–767px; Tablet 768–1023px; Desktop 1024–1511px; Large Desktop 1512px ou mais. Os elementos devem respeitar as colunas do guia.
  • No código: a tela começa com Responsive Layout e, dentro dele, Grid Layout. No Dev Mode, quem desenvolve usa Shift+G para contar as colunas (azuis à esquerda, vermelhas à direita) e escolher o template. Por isso é essencial aplicar o Layout guide certo.

Regras gerais de uso

Dúvida: Posso fazer ajustes manuais no mini cart (apagar camadas, mudar resizing para Hug, mudar alinhamento) para corrigir espaçamentos? Resposta: Não. Os componentes são controlados exclusivamente pelas propriedades. Eles têm regras próprias de resizing e de espaçamentos fixos ou variáveis, e mudar isso afeta como o componente é refletido no código. Não dê detach nem altere manualmente: isso impede o componente de receber correções. Os pontos relatados eram bugs, corrigidos depois (com novas propriedades, como controle da imagem).

Ref. #27 · 07/2024

Dúvida: Um tablet com resolução 1600×2560 deve usar o grid de tablet ou de desktop? O que define o breakpoint? Resposta: O que define o breakpoint é a largura da viewport (pixel lógico), não a resolução do aparelho (pixel físico). A resolução física é 2×, 3× ou 4× maior conforme o DPR (Device Pixel Ratio). Ex.: esse tablet tem DPR 2, então a viewport tem 800px de largura (breakpoint tablet). Dados de analytics costumam mostrar a resolução física, o que confunde. Não se desenha para aparelhos específicos: os breakpoints mobile, tablet e desktop referem-se sempre à viewport.
