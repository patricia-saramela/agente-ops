Design System — dúvidas do suporte

Resumo das dúvidas respondidas pelo time de System Ops no canal de suporte do Design System da empresa (discussions de 04/2024 a 11/2026, categoria Design System). Cada dúvida foi reescrita de forma genérica e anônima, com a orientação dada pelo time.

Complementa os arquivos ds-componentes-props (props de cada componente) e ds-figma-x-codigo (Figma × código).

Como usar esta base (instruções para o agente)

  • Responda em português. O público principal são designers.
  • Esta base registra orientações práticas dadas em casos reais. Quando houver conflito com a documentação de props, a documentação do componente vale para o que existe; esta base vale para como usar e o que é permitido.
  • Itens marcados ⚠️ limitação atual descrevem algo que o componente não faz na data da resposta e pode ter mudado depois. Cite a data (Ref. #n · mês/ano) ao responder.
  • Respostas mais recentes prevalecem sobre as mais antigas no mesmo assunto.
  • Quando a resposta for "valide com Pesquisa e Evolução" ou "com a liderança", é porque a decisão é de produto/conceito, não do Design System. Diga isso ao usuário.
  • Skins: a skin padrão é a Skin; a Skin Evolution é a versão nova. "Nova versão do app (5.0)" é a nova geração do app, com componentes em Flutter.
  • Não invente regras: se a dúvida não estiver aqui nem nos outros arquivos, diga que não há orientação registrada e sugira abrir uma discussão no canal de suporte.

Princípios que se repetem nas respostas

  • Componentes são controlados só pelas propriedades. Não dê detach, não mude paddings, gaps, resizing, tokens de cor ou presets manualmente. Isso quebra o vínculo com o código e impede atualizações. Se a variação não existe, abra uma solicitação de melhoria.
  • Mantenha as bibliotecas atualizadas e, se algo estiver estranho, use Reset instance antes de reportar.
  • Use a biblioteca da plataforma certa: Desktop no desktop e Mobile no mobile/tablet. Não misture bibliotecas, nem nos slots.
  • Slots só aceitam componentes, e alguns slots funcionam só na web (ex.: Sheet). No app, sheets e navegação são nativos e têm limitações.
  • Construção atômica: quando não existe componente, monte com componentes do Design System (ex.: Box + Rows, Circle + Text Timer, Meter no slot de um card) em vez de criar algo novo do zero.
  • Novos padrões de tela ou de uso precisam ser validados com a liderança e com Pesquisa e Evolução; System Ops orienta sobre os componentes.
  • Dúvidas de implementação (código) devem ir para o canal de suporte de desenvolvimento do Design System; o suporte de Ops cobre a camada de design.
  • Bugs de componente: abra pelo formulário de bug do repositório de suporte.
  • Reticências (truncamento) devem ser evitadas: prejudicam a acessibilidade e a compreensão.
  • Arquivos de conceito não são referência de documentação: use os guias oficiais (guia de fundamentos, Guia de Padrões da nova versão do app, Master).

Como solicitar a validação de jornada para System Ops

Tema: Validação de jornadas

  • A validação é obrigatória e acontece antes do handoff para desenvolvimento: é a etapa final do projeto. As telas devem estar na página de Handoff do arquivo.
  • Antes de enviar, é obrigatório rodar o plugin de validação de System em todas as jornadas que usam o Design System (ver o guia do plugin).
  • Passos: (1) preencha o formulário oficial de validação de jornada no repositório; (2) informe o link da página/frame a validar (preenchido na 1ª validação, atualizado a cada rodada e mantido no arquivo como histórico); (3) use o componente Notas da biblioteca Helper (Handoff & Acessibilidade) para registrar feedbacks; (4) consulte o guia "Erros comuns na validação de jornadas" antes de abrir o chamado; (5) qualquer alteração depois da aprovação exige revalidação (no mesmo ticket ou como subtarefa).
  • O time de Ops deixa notas no arquivo com os ajustes. Elas só podem ser removidas depois da aprovação. Durante a validação, o designer não deve alterar a estrutura do arquivo.
  • Status registrados no histórico do Figma: 🔵 início da validação · 🟠 validação com pendências (o designer corrige e disponibiliza de novo) · 🟢 aprovada · 🔴 reprovada.
  • ⚠️ Se os ajustes não forem feitos em 30 dias, a validação é reprovada e o ticket é fechado. Para recomeçar, é preciso abrir nova solicitação.

Erros mais comuns na validação de jornadas no Figma

Tema: Validação de jornadas

(corrija antes de pedir a validação): 1. Color styles de bibliotecas descontinuadas (ex.: a biblioteca antiga da marca, marcada como deprecated). Acontece ao copiar telas de arquivos antigos, usar componentes de fora das bibliotecas oficiais, não atualizar componentes ou colar textos sem Paste and match style. Correto: cores como variables (ícone quadrado no painel) vindas da biblioteca Skins do Design System. Se a cor continuar errada após atualizar, use Reset instance ou puxe uma nova instância da aba Assets. Exceções: gradientes (o Figma não suporta gradiente em variable, então ficam como color style) e elementos externos com cores próprias (ex.: logo de bandeira de cartão, em hexadecimal). 2. Cor errada no fundo da tela (hexadecimal #FFFFFF direto, ou color styles antigos). Correto: variables background (fundo branco) ou backgroundAlternative (cinza claro), da biblioteca Skins. Exceção: os componentes de sucesso de fim de fluxo (Success Feedback e Success Feedback Screen) usam a cor brand de fundo. 3. Text styles de bibliotecas descontinuadas. Correto: text styles da biblioteca Skins, atualizados. Se continuar errado, Reset instance. Ao colar textos, use Paste and match style (Cmd+Shift+V). Exceção: alguns componentes não usam text style e sim variables separadas (font size, line height, font weight); confira se a instância mantém as mesmas variables do original. 4. Telas sem Layout guide do Design System. Aplique o Layout guide adequado à largura: até 767px → Mobile; 768–1023px → Tablet; 1024–1511px → Desktop; 1512px ou mais → Large Desktop. E ao layout: templates 8+4, 6+6, 5+4, 4+6, 3+9 ou 12 (sem template). 5. Alterar manualmente propriedades de componentes. Ex.: para um Button Primary menor, use a propriedade booleana Small, nunca mude font size, line height ou padding na mão. Se a variação não existe como propriedade, não altere o componente. Sempre confira as propriedades disponíveis e não mexa em gap, padding, texto ou cor pelo painel. - Componentes da biblioteca Extended liberados para uso têm o sufixo (ext) (ex.: Data Progress (ext), Detailed Card (ext), Input Large (ext), Toggle Icon (ext)). Não use text styles da Extended: todos já existem na biblioteca Skins. - Outros erros frequentes: não nomear os frames; usar divider na última Row de uma lista; usar só Text Field num formulário que pede dados diferentes (telefone, CPF, data → use os campos específicos); usar mais de um Callout na mesma tela; usar a tela de feedback errada (ex.: Info Feedback Screen num erro de fim de fluxo, em vez de Error Feedback Screen); posicionar a Snackbar no lugar errado; usar ícone que não existe na biblioteca de ícones; usar cores incorretas em ícones; usar Nav Bar da biblioteca Extended em vez da biblioteca Modules ou da biblioteca Mobile.

Playroom

Tema: Ferramentas > Playroom

Ambiente de código voltado ao design para criar mockups e protótipos com os componentes reais do Design System, testar e compartilhar. Como criar layouts de acordo com o Design System

Tema: Layout e grid

  • Responsive Layout controla os breakpoint ranges e as margens laterais. São 4: Small, Medium (768–1023px), Large (1024–1511px) e Extra Large. Em Small, Medium e Large as margens são fixas e a área útil varia; em Extra Large a área útil é fixa e as margens crescem com a tela.
  • Grid Layout distribui o conteúdo em colunas; quantidade, largura das colunas e gutter mudam por breakpoint. Templates (úteis em Large e Extra Large): 6+6; 8+4; 4+6 (esquerda nas colunas 1–4, direita 6–11); 5+4 (esquerda 2–6, direita 8–11); 3+9. Os templates não são obrigatórios, mas são recomendados.
  • No Figma não existem componentes Responsive Layout nem Grid Layout: a biblioteca Desktop do Design System tem Layout guides equivalentes. Para aplicar: adicione a biblioteca Desktop → selecione o frame → no painel direito, Layout guides → Apply styles (ícone de 4 bolinhas) → escolha a opção. Shift+G mostra/esconde o guia. Mesmo sem template, aplique um Layout guide da categoria 12. Larguras: Mobile 320–767px; Tablet 768–1023px; Desktop 1024–1511px; Large Desktop 1512px ou mais. Os elementos devem respeitar as colunas do guia.
  • No código: a tela começa com Responsive Layout e, dentro dele, Grid Layout. No Dev Mode, quem desenvolve usa Shift+G para contar as colunas (azuis à esquerda, vermelhas à direita) e escolher o template. Por isso é essencial aplicar o Layout guide certo.
