  • Vale a largura da viewport (pixel lógico), não a resolução física do aparelho. Ex.: um tablet de 1600×2560 com DPR 2 tem 800px de viewport, então é tablet.
  • Tablet deitado com 1024px ou mais de largura passa a se comportar como desktop (grid e componentes de desktop).
  • ⚠️ A altura também conta: uma tela com menos de 550px de altura é tratada como celular, mesmo que seja larga (ex.: celular deitado, janela de navegador bem baixa).
  • Quando este documento diz "celular", "tablet" e "desktop", valem essas faixas. "Desktop" inclui os três tamanhos de desktop.

Web, webview e app

As regras de comportamento desta base descrevem o código web do Design System (React), usado em sites e nas telas web abertas dentro do app (webview). Alguns componentes mudam dentro do app:

  • Dentro do app (webview): Alert e Confirm viram o alerta nativo do sistema; o Snackbar é mostrado pelo próprio app; os tipos prontos do Sheet usam o visual nativo; a lista do Select, o calendário do Date Field e os seletores de data/hora são do sistema; a barra de navegação e a tab bar são nativas (um Sheet web fica por baixo delas).
  • Em aparelhos iOS, Checkbox, Radio, Switch e Slider usam sozinhos o visual do sistema. Não existe visual específico de Android: vale o visual Web.
  • O que está descrito aqui sobre o app vale para a versão atual do app. No app 5.0 pode ser diferente (ver a seção abaixo).

App 5.0 e versão atual

  • O app 5.0 é a nova versão do app, que faz parte de uma atualização de diretrizes em andamento. Ele usa a skin Evolution, componentes em Flutter e um Guia de Padrões próprio.
  • Algumas regras desta base valem só para a versão atual e podem mudar no app 5.0. Exemplos registrados pelo suporte: o sheet nativo sem slot e sem ícones da biblioteca, e a barra de navegação nativa por cima do sheet, que devem deixar de ser limitações no app 5.0.
  • Nas dúvidas do suporte, "nova versão do app" ou "nova versão do app (5.0)" se refere ao app 5.0.
  • As alterações específicas do app 5.0 terão uma documentação própria. Quando esta base não falar do app 5.0, a referência é o Guia de Padrões da nova versão do app.

Grid, margens e layout

  • No código, a tela começa com o Responsive Layout (margens laterais) e, dentro dele, o Grid Layout (colunas). No Figma eles não existem como componente: o equivalente são os Layout guides da biblioteca Desktop (Shift+G mostra/esconde). Toda tela precisa de um Layout guide do Design System.
  • Margens laterais: 16px no celular, 32px no tablet (768px), 48px no desktop (1024px), 64px no desktop grande (1512px). No desktop extragrande (1832px), as 12 colunas ficam centralizadas com largura fixa e as margens crescem com a tela. Conteúdo centralizado com margens grandes em monitores grandes é o comportamento esperado, não bug.
  • Espaço entre colunas (gutter): 24px no desktop e 16px no tablet.
  • Modelos de duas colunas: 6+6, 8+4, 7+5 (só no código), 4+6 (esquerda nas colunas 1–4, direita 6–11), 5+4 (esquerda 2–6, direita 8–11; usado em funil) e 3+9; e de uma coluna: 12, 10 e 8. Os modelos são recomendados, não obrigatórios. No 8+4, as 8 colunas são fixas e as 4 "móveis": o espaço entre os dois blocos varia com a largura da tela (não é erro).
  • No celular (e, por padrão, no tablet), as colunas viram uma só: o bloco da esquerda fica em cima e o da direita embaixo.
  • Listas (Row/Boxed Row) no desktop ocupam 8 colunas do grid de 12 (use o modelo 12 ou 8+4).
  • Inputs têm largura mínima, mas não máxima fixa: escalam com as colunas (podem ocupar 6 ou 8 colunas). No desktop, sem "largura toda", o campo tem 328px no código (o componente do Figma tem 496px): informe qual usar.
  • O Design System não define rolagem de interface (ex.: só a lista rolar com o título fixo): é decisão de produto.
  • O Design System não tem regra rígida de múltiplos de 4/8, embora os siga na maioria dos casos.

Fundos e cores (Theme context)

  • No Figma, a propriedade Theme context diz sobre qual fundo o componente está. No código ela não é uma prop: a cor vem do fundo onde o componente está (a faixa da página com variant). Os fundos são: Default (branco), Alternative (cinza claro), Brand/Inverse (cor da marca), Negative (escuro) e Media (sobre imagem).
  • A maioria dos componentes troca de cor sozinha conforme o fundo. Não trocam (ficam com as cores do fundo padrão): Select, Table, Tag em fundo Negative, Timeline em fundo Negative e o conteúdo do Tooltip (só a borda muda).
  • Para um elemento branco numa tela de fundo cinza (ex.: Callout), declare o fundo Alternative no container: o componente se ajusta sozinho para fundo branco.
  • Cores e textos vêm sempre da biblioteca Skins (variables e text styles). Fundo de tela: background (branco) ou backgroundAlternative (cinza claro). Exceção: telas de sucesso de fim de fluxo usam fundo brand.
  • Não existe como aplicar opacidade livre a uma variável (ex.: background a 3%): use só as variáveis que já existem (algumas, como backgroundSelected, já têm transparência embutida). Não se trocam tokens de cor dos componentes à mão (ex.: subtitle da Row, cor do Text Link, borda de card). inputBorder é só para campos de formulário; para outros elementos, border.
  • Imagens: raio de 16px; quando estão dentro de um container (Row, card), o raio passa a ser 8px.

Bibliotecas do Figma

  • Desktop (telas ≥1024px, componentes com sufixo [D]) e Mobile (celular e tablet, ≤1023px). Não misture as duas, nem dentro de slots.
  • Skins: variables de cor e text styles da marca (skin padrão e skin Evolution). Extended: componentes exclusivos da marca, liberados com o sufixo (ext), com código e Storybook próprios (não use text styles da Extended). A Extended terá uma base de conhecimento própria. Modules: templates só para o Figma (os devs não consomem componentes dela). Assets: logos, bandeiras de cartão, redes sociais. Helper: recursos de handoff e acessibilidade (componente Notas).
  • Bibliotecas legadas (Portal, Loja, Hybris, Agile, DS B2B antigo) atendem jornadas que ainda não migraram: use uma só, nunca misture com o Design System na mesma jornada.

Princípios de uso (valem para quase todas as respostas)

  • Componentes são controlados só pelas propriedades. Não dê detach nem altere padding, gap, resizing, tokens de cor ou presets de texto à mão. Se a variação não existe, o caminho é a solicitação de melhoria.
  • Mantenha as bibliotecas atualizadas. Antes de reportar problema, use Reset instance.
  • Slots só aceitam componentes (transforme o conteúdo em componente e use Swap instance). Alguns slots funcionam só na web (ex.: Sheet Slot (Only web)).
  • Se não existe um componente, prefira construção atômica com componentes do Design System em vez de criar algo do zero.
  • Evite reticências e truncamento: prejudicam a acessibilidade. Prefira textos curtos (time de conteúdo).
  • Use o componente do tipo de dado certo (Email Field, Phone Number Field, Date Field…) em vez de só Text Field.
  • Arquivos de conceito não são referência de documentação. Use os guias oficiais (guia de fundamentos, Master, Guia de Padrões da nova versão do app).
  • Área de toque mínima: 48px (o código garante isso nos botões de ícone, mesmo no pequeno).
  • Um texto de título deve usar o componente Title só se for de fato um título; cada página tem um único título principal (h1).
  • Tipografia muda por tamanho de tela: use os presets da plataforma certa (ex.: text-preset-3 tem 18px no desktop e 16px no celular; o helper text dos campos tem 12px no celular e 14px no desktop). O tamanho dos Titles também muda com o breakpoint.
